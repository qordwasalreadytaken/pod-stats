🎯 Project Overview

This project automatically fetches Path of Diablo ladder data, generates analytics pages with charts, and deploys them to GitHub Pages. The entire process is automated through GitHub Actions workflows.

Key Components:

  • Data Source: Path of Diablo API (ladder data)
  • Processing: Python scripts in scripts/ directory
  • Output: HTML pages with interactive charts
  • Deployment: GitHub Pages (automatic)
  • Tracking: CSV files for historical usage data

⚙️ GitHub Actions Workflows

All workflows are located in .github/workflows/ directory. Here's what each one does:

📊 Update and Deploy (update-and-deploy.yml)
✅ ENABLED

Purpose: This is the MAIN PRODUCTION WORKFLOW that keeps the site updated with fresh data and deploys it to GitHub Pages.

🕐 When It Runs:

Scheduled:
Twice daily at 7:00 AM and 7:00 PM UTC
Push Trigger:
Every time code is pushed to the main branch
Manual:
Can be triggered manually from GitHub Actions tab

📋 What It Does:

  1. Data Update Phase:
    • Runs python3 scripts/generate_pages.py --page dataupdate
    • Fetches fresh API data (server stats, game servers, character data)
    • Updates unified-usage-over-time.csv with new snapshot
    • Generates tracking pages (sc-usage-over-time.html, hc-usage-over-time.html, server-stats-over-time.html)
  2. Page Generation Phase:
    • Generates all Softcore pages with --page all --mode sc
    • Generates all Hardcore pages with --page all --mode hc --hc-level-filter 70
    • Includes: home pages, fun facts, items/equipment, mercenary pages, all class pages
    • Creates interactive charts saved to charts/ directory
  3. Commit Phase:
    • Commits updated HTML, CSS, JS, JSON, and CSV files
    • Pushes changes to main branch
    • Cleans up Python cache files
  4. Deploy Phase:
    • Automatically deploys to GitHub Pages
    • Uses actions/deploy-pages@v4
    • Site becomes live at the configured GitHub Pages URL

🎯 Why This Exists:

This workflow ensures the analytics site always has fresh data without manual intervention. It runs twice daily to capture ladder changes at peak times and also regenerates pages whenever code changes are pushed.

🛡️ Season Freeze Protection:

This workflow includes automatic season freeze detection. When a Path of Diablo season ends, the workflow will:

  • Detect that the season has ended (no new season info available yet)
  • STOP generating new pages to preserve the final season state
  • Display a freeze banner on the live site
  • Wait until the new season officially starts before resuming updates

Why this matters: During the brief period between seasons (usually a few days), we want to preserve the complete final ladder state. Without the freeze, the site would show an empty ladder as everyone's characters are wiped for the new season.

If you need to update pages during a freeze (e.g., bug fixes), use the Force Update workflow below, which bypasses this protection.

⚠️ Important Notes:

  • This workflow has contents: write and pages: write permissions
  • Uses concurrency control to prevent multiple deploys at once
  • The needs: update-data ensures deploy only happens after successful data update
  • DO NOT DISABLE THIS unless you want to stop all automatic updates
  • Season freeze detection is built into generate_pages.py
📡 Daily Ladder Fetch (daily-ladder-fetch.yml)
✅ ENABLED - CRITICAL

Purpose: FOUNDATION WORKFLOW - Fetches the raw ladder data that ALL other workflows depend on.

🕐 When It Runs:

Scheduled:
Daily at 6:00 AM UTC
Manual:
Can be triggered manually from GitHub Actions tab

📋 What It Does:

  1. Runs cd scripts && python fetch_ladder_data.py
  2. Fetches Softcore ladder data from Path of Diablo API
  3. Fetches Hardcore ladder data from Path of Diablo API
  4. Moves sc_ladder.json and hc_ladder.json to root directory
  5. Commits and pushes the JSON files with timestamp
  6. Logs character counts for both ladders

🎯 Why This Exists:

This is the DATA SOURCE for the entire project. It runs early in the morning (6 AM UTC) to fetch fresh ladder data, creating the JSON files that every other workflow depends on:

  • sc_ladder.json - Complete Softcore ladder data
  • hc_ladder.json - Complete Hardcore ladder data

These files contain all character information: class, level, skills, equipment, mercenary gear, etc. Without this workflow, no other workflows can function.

📊 Data Flow:

Daily Ladder Fetch (6 AM UTC) ↓ Creates sc_ladder.json & hc_ladder.json ↓ Update and Deploy (7 AM & 7 PM UTC) ↓ Reads JSON files → Generates pages → Deploys

⚠️ Important Notes:

  • NEVER DISABLE - This is critical infrastructure
  • Runs 1 hour BEFORE update-and-deploy to ensure fresh data is available
  • If this fails, all page generation workflows will use stale data
  • JSON files are committed to repo, providing data persistence
  • Uses pip install requests matplotlib for dependencies
🔧 Force Update (force-update.yml)
✅ ENABLED (Manual Only)

Purpose: Emergency workflow to force page regeneration, bypassing season freeze protections.

🕐 When It Runs:

Trigger:
MANUAL ONLY - Must be triggered from GitHub Actions tab

📋 Input Parameters:

update_mode: - both (default) - Generate SC and HC pages - softcore - Generate SC pages only - hardcore - Generate HC pages only page_type: - all (default) - All pages + dataupdate - home - Home page only - funfacts - Fun facts page only - items - Items/equipment page only - mercenaries - Mercenary page only - class - Class pages only reason: - Text field for logging why you ran the force update

📋 What It Does:

  1. Checks current season status (but proceeds regardless)
  2. If page_type == 'all', runs dataupdate first
  3. Runs page generation with --force flag
  4. Bypasses the season freeze protection
  5. Commits and pushes changes

🎯 Why This Exists:

The normal workflow respects season freeze periods (when a season ends). This workflow lets you update pages anyway, useful for:

  • Fixing bugs during a freeze period
  • Testing new features
  • Emergency content updates
  • Regenerating pages after manual data changes

⚠️ Important Notes:

  • Use sparingly - this bypasses safety mechanisms
  • Always provide a reason in the reason field
  • The reason gets logged in the commit message
  • Won't trigger automatic deploy - must be handled separately
🗄️ Monthly Archive (monthly-archive.yml)
✅ ENABLED

Purpose: Automatically creates monthly snapshots of ladder data for historical preservation.

🕐 When It Runs:

Scheduled:
28th of every month at 2:00 AM UTC
Manual:
Can be triggered manually

📋 What It Does:

  1. Runs python scripts/api_integration.py archive monthly
  2. Determines current season number and month name
  3. Creates archive directory at Season/X/MonthName/
  4. Copies current ladder JSON files to archive
  5. Generates static HTML pages for the archive
  6. Copies all charts to archive
  7. Includes CSS, icons, and assets for standalone viewing
  8. Commits and pushes the archive

🎯 Why This Exists:

Path of Diablo seasons last several months. This workflow creates monthly snapshots showing how the meta evolved during the season. Each archive is a complete standalone website that can be viewed independently.

📁 Archive Structure:

Season/ ├── 1/ │ ├── November/ │ │ ├── index.html │ │ ├── sc_ladder.json │ │ ├── hc_ladder.json │ │ ├── Home.html │ │ ├── FunFacts.html │ │ ├── charts/ │ │ └── css/ │ ├── December/ │ └── Final/ └── 2/

🛡️ Season Freeze Behavior:

Monthly archives are NOT affected by season freeze protection. They will continue to run on schedule regardless of season status:

  • During active season: Creates monthly snapshot of current ladder state
  • After season ends: Still runs and creates final monthly snapshot
  • Between seasons: Continues working (though data may be empty)

This is intentional - monthly archives preserve the timeline of the season, including the transition period.

⚠️ Important Notes:

  • Archives are large (includes all data + generated pages)
  • Each archive is self-contained and can be viewed independently
  • The 28th was chosen as a safe date (all months have 28+ days)
  • Archive generation takes several minutes
  • Unlike page generation, archives ignore freeze protection
📦 Manual Archive (manual-archive.yml)
✅ ENABLED (Manual Only)

Purpose: Create archives on-demand, including final season archives.

🕐 When It Runs:

Trigger:
MANUAL ONLY - Must be triggered from GitHub Actions tab

📋 Input Parameters:

archive_type: - monthly (default) - Create a monthly snapshot - final - Create the final season archive force_creation: - false (default) - Respect season timing - true - Force archive creation regardless of season status

📋 What It Does:

  1. Runs python scripts/api_integration.py archive [type]
  2. Creates archive in appropriate directory
  3. For "final" type, creates Season/X/Final/ directory
  4. Same archive generation as monthly workflow
  5. Verifies archive was created successfully
  6. Commits and pushes

🎯 Why This Exists:

Two main use cases:

  • Extra Monthly Archives: Create additional snapshots if something interesting happens mid-month
  • Final Season Archive: When a season ends, create the definitive "Final" archive that represents the complete season

🛡️ Season Freeze Behavior:

Manual archives respect season timing by default but can be forced:

  • Monthly archives: Always allowed regardless of season status
  • Final archives: Only allowed when season has ended (respects freeze)
  • With force_creation=true: Bypasses all timing checks for both types

When to use force_creation: If season detection is having issues or you need to create a final archive before the system recognizes the season has ended.

⚠️ Important Notes:

  • Use archive_type: final when a season ends
  • The "Final" archive is special - it's the canonical record of that season
  • Force creation only needed if season detection is having issues
  • Manual monthly archives overwrite existing monthly archives for that month
  • Unlike live page generation, monthly archives ignore freeze protection

🔧 Enabling/Disabling Workflows

To Enable a Workflow:

  1. Go to GitHub repository
  2. Click "Actions" tab
  3. Find the workflow in the left sidebar
  4. If it shows "This workflow is disabled", click "Enable workflow"
  5. The workflow will start running on its schedule or can be triggered manually

To Disable a Workflow:

  1. Go to GitHub repository → Actions tab
  2. Click the workflow name
  3. Click the "..." menu in the top-right
  4. Select "Disable workflow"
  5. Confirm the action

🔧 Troubleshooting

Workflow Failed - What Do I Check?

  1. Go to Actions Tab: Click on the failed workflow run
  2. Expand Failed Step: Click on the red X to see error details
  3. Common Issues:
    • API Rate Limit: PoD API may be down or rate-limiting. Wait and retry.
    • Python Dependency Error: Check if requirements.txt is up to date
    • Permission Error: Workflow needs contents: write permission
    • Archive Creation Failed: Check Season directory exists and is writable

Site Not Updating

  1. Check if update-and-deploy.yml is enabled
  2. Look at recent workflow runs - are they succeeding?
  3. Check GitHub Pages settings (Settings → Pages) - should be deploying from gh-pages branch or GitHub Actions
  4. Clear browser cache - updates may be cached

Archive Not Created

  1. Check if monthly-archive.yml ran (Actions tab)
  2. Look at archive verification step - did it find the expected directory?
  3. Manually trigger manual-archive.yml with force_creation=true
  4. Check Season/ directory in repository - archives should be there

Emergency: Need to Update Site But Workflow Failing

  1. Clone repository locally
  2. Run commands manually:
    cd scripts python3 generate_pages.py --page all --mode sc python3 generate_pages.py --page all --mode hc
  3. Commit and push changes
  4. GitHub Pages will deploy automatically

Need to Disable Everything

If something catastrophic happens and you need to stop all automation:

  1. Go to Settings → Actions → General
  2. Under "Actions permissions", select "Disable actions"
  3. This stops ALL workflows immediately
  4. Re-enable when ready: "Allow all actions and reusable workflows"
